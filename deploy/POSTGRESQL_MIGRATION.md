# Перенос Synapse на PostgreSQL в AlwaysData

Рабочий SQLite остаётся источником истины до завершения проверки. Не
запускайте две копии Synapse одновременно с разными базами: входящие
уведомления и Telegram-события разойдутся между ними.

## Подготовка

1. Создайте пустую базу `synapseivan_synapse` и разрешите доступ только
   PostgreSQL-пользователю сайта. Пароль держите в `~/.pgpass` (права `0600`)
   либо в секретном поле окружения AlwaysData. Не записывайте его в Git.
2. Убедитесь, что есть свободное место для одновременного хранения SQLite и
   PostgreSQL. Штатная чистка удаляет только старые восстанавливаемые
   Telegram-вложения; остальные медиа и SQLite не удаляются.
3. Установите новые `requirements.txt` на сервере. Сохраните адрес старой
   SQLite-базы и действующий ключ `SKILLWOOD_ENCRYPTION_KEY`.

## Переключение

1. На время финального копирования замените путь WSGI-сайта в AlwaysData на
   `synapse/maintenance_wsgi.py`. Это останавливает приложение и его
   Telegram-процесс; Android-клиент получает HTTP 503 и не пишет в SQLite.
   Убедитесь, что прежний WSGI завершился. Сохраните прежний путь
   `synapse/wsgi.py` для возврата. Приём сообщений в этот период недоступен.
2. В окружении SSH задайте `SKILLWOOD_DATABASE_URL` с адресом пустой базы.
   Если используется `~/.pgpass`, пароль в URL не нужен. Не выводите URL с
   паролем в журнал команд.
3. Выполните `python -m scripts.migrate_sqlite_to_postgres --sqlite db/blogs.db`.
   Скрипт сначала проверяет SQLite, затем переносит 18 таблиц в одной
   транзакции, сверяет каждую колонку и выставляет последовательности ID.
   Старые вложения/правки без исходного сообщения сохраняются в отдельной
   таблице `synapse_orphan_rows`: их нельзя поместить в рабочие таблицы
   PostgreSQL с целостными внешними ключами. Исходная SQLite не меняется.
   При ошибке транзакция откатывается.
4. Задайте тот же `SKILLWOOD_DATABASE_URL` для WSGI, верните путь
   `synapse/wsgi.py` и запустите сайт. Проверьте
   `/api/ping`, вход, список чатов, отправку текста и фото в Telegram и MAX,
   приём нового сообщения и серверные ошибки. Сравните CPU и задержки с
   измерениями до переключения.
5. Только после успешной проверки оставьте PostgreSQL как рабочую базу.
   SQLite-файл пока храните как резервную копию. Запуск старой версии с этой
   SQLite после появления новых сообщений в PostgreSQL приведёт к потере
   части истории при следующем переключении.

## Откат

Если сайт не запускается до появления новых записей, уберите
`SKILLWOOD_DATABASE_URL` из окружения WSGI и перезапустите WSGI: старый
`SKILLWOOD_DB_PATH` снова выберет SQLite. Если новые записи уже поступали,
сначала сохраните PostgreSQL-базу и отдельно решите, как объединить новые
данные, не перезаписывая их старым SQLite.
